## 1. Outcome

### 1.1 User-visible outcome

Closes B-01/B-02/B-03 raised by T0 against F9 X4/X5. After F9-B, an assigned `HR_STAFF` writer:

- Sees only legitimately assigned slots from a normal RLS-scoped SELECT.
- Can acquire the canonical order-scoped advisory lock (`p1a04:order:<STAFFING_ORDER_ID>`).
- Can re-read assignment and mutable state after the lock.
- Can create + bind exactly one DRAFT JobOpening to that slot via the least-privilege `hrp_f9b_bind_slot_to_opening` SECURITY DEFINER function — which admits only ADMIN / HR_MANAGER / ACTIVE assigned HR_STAFF, locks and validates the slot, mutates ONLY `staffing_order_slots.job_opening_id`, accepts null→expected or idempotent same-ID replay, and rejects rebind / cross-slot / cross-order / missing identity / revoked / other recruiter / unassigned.
- Can then create/reuse the DRAFT JobPosting through the existing F9 narrow INSERT policy (`hrp_f9_postings_staff_insert`).
- Cannot mutate any other `staffing_order_slots` column directly (`position_title`, `position_code`, `work_location`, `slots_needed`, `slots_filled`, `valid_to`, `staffing_order_id`, arbitrary `job_opening_id` rebind — all denied).
- Cannot cross-order/cross-slot construction (inserting `staffing_order_id` of an assigned order with a `staffing_order_slot_id` of another order — denied).
- Cannot invoke the new primitive after revoke: a true two-connection race proves the post-lock re-read observes `REVOKED` and fails closed with one exact canonical code.

ADMIN and HR_MANAGER behavior remains byte-equivalent (the new primitive is bypassed for them via the `assertMutationRole` gate; they continue to use the broader RLS path for direct slot binding).
