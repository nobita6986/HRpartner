C-04 — Fail-closed delegation detector
=========================================

Round: 2 (v1.2) + F-02 substantive proof + F-04A call-expression closure +
F-04B helper injection for `helper_missing_security_markers`.

Change:
-------
File: `src/domains/applications/marketplace-inventory.static.test.ts`

Removed hard-coded `ADMIN_GUARDED_VIA_HELPER` allowlist (which v1.1 used
to enumerate specific route file names). Replaced with a SINGLE canonical
classifier function used by BOTH the production route inventory AND the
negative fixture:

  classifyMutatingPlacementRoute(file, options?) -> ClassificationResult
    Path A — route source has AUTH_MARKER call expression          -> guarded: true, path: 'A'
    Path B — route delegates to a `./handler` sibling whose source  -> guarded: true, path: 'B'
              has AUTH_MARKER call expression
    Path C — route imports `placement.route-helpers` AND           -> guarded: true, path: 'C'
              has actual `runPlacementCommand(` call AND the
              helper exports `runPlacementCommand` AND contains
              ACTUAL `getAuthContext(` AND `withDbContext(` call
              expressions
    ANY condition missing -> guarded: false, with specific reason:
      - 'no_helper_import'
      - 'no_helper_call'
      - 'helper_missing_security_markers'
      - 'no_direct_auth_call'            (F-04A)
      - 'no_delegate_handler_auth_call'  (F-04A)
      - 'no_handler_sibling'             (F-04A reserved)

F-04A — Bare-identifier bypass closure:
- AUTH_MARKER detection now uses `\bMARKER\s*\(` (call expression).
  Bare identifiers, `import` statements, `import type`, comments, and
  type annotations do NOT count.
- This applies to BOTH Path A (direct route AUTH_MARKER) and Path B
  (delegated handler AUTH_MARKER) — not only Path C/placement helper.
- New 5 F-04A substantive assertions verify:
  * direct route imports `getAuthContext` but never calls it → UNGUARDED
  * direct route has bare `getAuthContext` identifier only (in comment) → UNGUARDED
  * direct route ACTUALLY calls `getAuthContext(...)` → GUARDED via Path A
  * delegated handler imports marker but never calls it → UNGUARDED with reason
    `no_delegate_handler_auth_call`
  * delegated handler ACTUALLY calls marker → GUARDED via Path B

F-02 SUBSTANTIVE PROOF (round-2):
- Marker checks REQUIRE call expressions (`getAuthContext(`), not bare
  identifier presence. A comment like `// uses getAuthContext` no longer
  satisfies the check.
- The negative fixture
  `tests/security/admin-route-fail-closed.negative-fixture.ts` is run
  through the SAME `classifyMutatingPlacementRoute` function used by
  the production route inventory — so "proves detector catches" is
  now a measurable, reproducible assertion.

F-04B — `helper_missing_security_markers` injection:
- `classifyMutatingPlacementRoute(file, { helperSource?, helperExists? })`
  accepts an optional injected helper so tests can exercise the
  `helper_missing_security_markers` branch WITHOUT mutating the
  canonical production helper. Cleanup runs in `finally` AND before the
  post-cleanup existence check, so residue is impossible even on
  assertion failure.
- 3 new F-04B assertions:
  * helper exports runPlacementCommand with bare identifiers only →
    `{ guarded: false, reason: 'helper_missing_security_markers' }`
  * helper has no security markers at all → same reason
  * `helperExists: false` (simulating missing helper file) → same reason

Negative fixture (unchanged): `tests/security/admin-route-fail-closed.negative-fixture.ts`
  - declares `export async function POST`
  - does NOT import placement.route-helpers
  - does NOT call `runPlacementCommand`
  - does NOT contain `getAuthContext(` or `withDbContext(` call expressions
  - classifier returns `{ guarded: false, reason: 'no_helper_import' }`
