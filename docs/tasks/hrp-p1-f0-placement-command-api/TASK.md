## 1. Outcome

### 1.1 User-visible outcome (post implementation — TIER 1B implementation round, không phải round này)

- Recruiter (`ADMIN` hoặc `HR_MANAGER`; `HR_STAFF` → 403 theo C-02) gọi **5 named canonical placement commands** qua HTTP admin API:
  - `placement.create` — `POST /api/admin/placements` với `{ placementCaseId, jobOpeningId, sourceCandidateSubmissionId? }` + `Idempotency-Key: <UUID v4>` → 201 `{ placementId, status: 'SELECTED', serviceModelSnapshot, clientCompanyId, projectId, replayed }` (đúng `CreatePlacementResult` hiện hữu). Race-safe qua `placements_active_unique` partial unique index (DEC-04a). Idempotent replay khi cùng `(placementCaseId, jobOpeningId)`.
  - `placement.confirm` — `POST /api/admin/placements/[id]/actions/confirm` với body `{}` + `Idempotency-Key: <UUID v4>` → 200 `{ placementId, status: 'CONFIRMED', replayed }` (đúng `TransitionPlacementResult` hiện hữu — không thêm field). Conditional UPDATE với status guard (DEC-12). Service chỉ ghi `confirmedAt` (C-01).
  - `placement.effective` — `POST /api/admin/placements/[id]/actions/effective` với `{ evidence: { clientAcknowledgedAt: ISO-8601, clientAcknowledgedByUserId, acknowledgementRef } }` + `Idempotency-Key: <UUID v4>` → 200 `{ placementId, status: 'EFFECTIVE', replayed }` cho Client-managed thành công (đúng `TransitionPlacementResult` hiện hữu — KHÔNG có `placementCaseClosed` vì service không trả field này; AC-07 verify atomic close bên trong service qua DB inspection). **Chỉ Client-managed** (DEC-07). **HRP-managed** → REJECT với `PlacementValidationError` (code `PLACEMENT_VALIDATION_ERROR`) → HTTP 400 (KHÔNG 422; KHÔNG code `HRP_MANAGED_EFFECTIVE_NOT_SUPPORTED` — taxonomy freeze theo C-07). Evidence thiếu field / unknown fields → 400 `VALIDATION` hoặc `PLACEMENT_VALIDATION_ERROR`. Client-managed thành công → Placement EFFECTIVE + PlacementCase CLOSED atomic (AC-07), KHÔNG tạo Worker.
  - `placement.fail` — `POST /api/admin/placements/[id]/actions/fail` với body `{}` + `Idempotency-Key: <UUID v4>` → 200 `{ placementId, status: 'FAILED', replayed }` (đúng `TransitionPlacementResult` hiện hữu). SELECTED | CONFIRMED → FAILED (DEC-05). KHÔNG nhận `reason` (TransitionPlacementInput không có field; C-06). Service tự tạo `failureReason`.
  - `placement.cancel` — `POST /api/admin/placements/[id]/actions/cancel` với body `{}` + `Idempotency-Key: <UUID v4>` → 200 `{ placementId, status: 'CANCELLED', replayed }` (đúng `TransitionPlacementResult` hiện hữu). SELECTED | CONFIRMED → CANCELLED (DEC-05). KHÔNG nhận `reason` (C-06). EFFECTIVE là terminal → cancel sau EFFECTIVE bị `canTransition` REJECT → 409 `INVALID_STATE_TRANSITION` (C-01).
- Tất cả route dùng **đúng một transaction boundary**: `getAuthContext` → role gate (ADMIN/HR_MANAGER) → strict body parsing → `withIdempotency` → `withDbContext(getPrisma(), ctx, tx => placement.service)`. KHÔNG dùng `withAuthorizedDb` cho create/write (DEC-03 — L1 không safe với `create`). KHÔNG mở transaction lồng nhau giữa route và adapter.
- Tất cả route gọi service thuần (`createPlacement`/`confirmPlacement`/`markPlacementEffective`/`failPlacement`/`cancelPlacement`) — KHÔNG sửa `placement.service.ts`.

#### 4.1.2 Transaction shape (locked — C-03)

```
route handler (single transaction boundary):
  ctx = getAuthContext(req)              // 401 nếu thiếu/invalid
  role gate                              // 403 nếu ctx.role != ADMIN && != HR_MANAGER
  body = parseStrict(req)                // 400 VALIDATION nếu shape sai
  key = req.headers['Idempotency-Key']   // 400 IDEMPOTENCY_REQUIRED nếu thiếu/invalid
  result = await withIdempotency({ actorId: ctx.userId, routeName, key, payload }, async () =>
    withDbContext(getPrisma(), ctx, tx =>
      placement.commands[command](tx, buildInput(body, ctx, params))
    )
  )
  return mapToHttp(result)               // exact service result → response
```

KHÔNG có transaction lồng nhau; KHÔNG wrap `withDbContext` hai lần.
